# 인물 지식 그래프 + 에이전트 체인 + 노출 KPI 설계

작성일: 2026-08-15
관련 기존 시스템: `naver-article` / `write-article` 스킬, `docs/지침/01~05`, `scripts/check-article.mjs`,
`supabase/functions/discord-notify`, 네이버 통합검색 스크린샷 크론(`2026-05-25-naver-search-screenshot-discord-design.md`)

---

## 1. 배경

원고 생산은 이미 돈다. 발행 1,397건, 인물 후보 6,139건이 쌓여 있다. 문제는 품질이 아니라
**검색 노출**이고, 더 정확히는 **노출됐는지를 측정하지 않는다는 것**이다.

현재 매일 10:00 KST에 전일 발행 키워드를 네이버 통합검색에 검색해 스크린샷을 Discord로 보낸다.
그런데 그 결과가 어디에도 저장되지 않고, **노출되지 않은 키워드는 조용히 skip된다**
(해당 설계 문서 "스코프 밖: 노출 결과 히스토리 DB 저장"). 즉 실패 사례가 통째로 사라진다.

측정이 없으니 원고를 어떻게 고쳐야 노출이 오르는지 판단할 근거가 없다. 밀도 기준을
3~5회/1000자로 전환한 것(a12d8e6)도 효과를 확인할 수단이 없는 상태에서의 조정이었다.

동시에 사용자는 이 데이터를 원고 생산에만 쓰지 않고 **부가 서비스의 자산**으로 쓰려 한다 —
섭외 추천·매칭, 공개 인물 데이터베이스, 문의 자동응답.

## 2. 목표와 비목표

### 우선순위 — 상위 노출이 최우선이다

**이 프로젝트의 1순위는 `"<인물명> 섭외"` 검색의 상위 노출이다.** 지식 그래프도, 부가 서비스도
그 아래다. 판단이 갈릴 때마다 "이것이 노출에 기여하는가"로 정한다.

- 지식 그래프가 1단계에 들어가는 이유는 그 자체가 목적이어서가 아니라, **경쟁 글이 못 다루는
  정보 축을 원고에 넣을 재료**이기 때문이다(DIA+ 정보 충실성·독창성).
- 부가 서비스 3종(§11)은 **노출 지표가 실제로 개선 추세를 보인 뒤에** 착수한다. 그 전에는
  설계도 하지 않는다 — 노출이 안 되는 상태에서 서비스를 얹으면 재료가 되는 데이터 자체를 못 믿는다.

### 목표

1. `"<인물명> 섭외"` 검색 시의 색인 여부·순위를 KPI로 상시 기록한다.
2. 원고 작성을 수집·검증·작성·검수 4단계로 분리해 근거 없는 문장을 구조적으로 막는다.
3. 원고 생산 과정의 부산물로 인물 지식 그래프가 자동으로 쌓이게 한다 — 원고의 정보 독창성을 위한 재료다.
4. 키워드 밀도 같은 대리 지표를 의미 기반 지표로 대체하고, **그 지표 자체를 KPI로 검증**한다.
   **측정 수단이 실패해도 측정을 포기하지 않는다** — 대체 수단으로 내려간다(§7.4).

### 비목표 (이번 설계 범위 밖)

- 기존 발행 원고 1,402건에서의 지식 역추출 — 검증되지 않은 정보를 굳히는 위험이 크다.
- 출연료 금액 추정 — 어떤 형태로도 산출·표시하지 않는다(§7.3).
- 추천·매칭 / 공개 인물 DB / 문의 자동응답 — 후속 단계(§11). 그래프가 실제로 어떻게 차는지
  보기 전에 설계하면 틀린 가정 위에 짓게 된다.
- 하이브 계열 아티스트 신규 수집 — 2026-06-29 공지로 이미 `keywords.is_active=false`. 그래프도 동일 적용.

## 4. A — 노출 KPI 기록

### 4.1 KPI 정의

원고의 목표 쿼리는 고정이다: **`"<인물명> 섭외"`**. 제목 규칙이 이미 `[인물명 섭외]`로
시작하도록 강제하고 있다. 따라서 검색어 선정·경쟁 쿼리 조사는 불필요하다.

**두 검색면을 각각 잰다.** `blog-tab`(블로그 탭)이 색인 여부를, `pc-total`(통합검색)이
실제 노출과 순위를 알려준다. 통합검색만 재면 둘이 한 덩어리가 되어 원인 진단이 불가능하다.

| 지표 | 의미 | 왜 분리하나 |
|---|---|---|
| `indexed` @ `blog-tab` | 네이버가 이 글을 색인했는가 | 색인 실패는 원고 문제가 아니다. 계정 지수·발행 패턴 문제다 |
| `indexed`·`rank` @ `pc-total` | 통합검색에 올라왔는가, 몇 번째인가 | 색인은 됐는데 통합검색에 못 들어간 것 — 원고 경쟁력 문제다 |
| `first_seen_at` | 처음 잡힌 시각 | 색인 지연 자체가 계정 건강 지표다. 별도 컬럼 없이 `indexed=true` 인 가장 이른 `checked_at` 으로 유도한다 |

### 4.1.1 첫 실측 (2026-08-15) — 이 분리가 왜 필요했는지

구현 직후 D+1/3/7/14/30 대상 60건(37쿼리)을 실제로 재 보았다.

| 검색면 | 잡힘 | 비고 |
|---|---|---|
| `blog-tab` | 36 / 60 (60%) | 순위 1~22위 분포 |
| `pc-total` | 9 / 60 (15%) | **잡힌 9건은 전부 1위** |

추가 표본: 2026-04 발행분은 두 검색면 모두에서 사라져 있었고(글 자체는 200 응답으로 살아 있음),
제목을 통째로 검색해도 나오지 않았다.

읽는 법: **통합검색에 진입만 하면 1위다.** 경쟁이 약한 롱테일 쿼리이므로 당연하다.
문제는 순위가 아니라 **진입률(15%)** 이고, 그 앞단에 **색인률(60%)** 이 있다.
따라서 원고 품질 개선이 겨냥할 것은 "1위로 올리기"가 아니라 **"통합검색에 들어가기"** 다.
색인조차 안 된 40%는 원고로 풀 문제가 아닐 개연성이 크다 — 계정·발행 패턴 쪽 별도 진단이 필요하다.

이 숫자가 §8 주간 분석의 기준선이 된다.

### 4.2 스키마

```sql
CREATE TABLE IF NOT EXISTS mih_serp_checks (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  article_id   uuid REFERENCES articles(id) ON DELETE CASCADE,
  query        text NOT NULL,              -- '<인물명> 섭외'
  checked_at   timestamptz NOT NULL DEFAULT now(),
  surface      text NOT NULL DEFAULT 'pc-total',  -- pc-total | mobile-total | blog-tab
  indexed      boolean NOT NULL,
  rank         smallint,                   -- 미노출이면 NULL
  competitors  jsonb NOT NULL DEFAULT '[]',-- [{rank, url, title, publisher}] 상위 5건
  screenshot   text,                       -- 스토리지 경로 (기존 크론 산출물 재사용)
  note         text
);

CREATE INDEX IF NOT EXISTS mih_serp_checks_article_idx ON mih_serp_checks (article_id, checked_at DESC);
CREATE INDEX IF NOT EXISTS mih_serp_checks_query_idx   ON mih_serp_checks (query, checked_at DESC);
```

- **미노출도 반드시 1행 남긴다** (`indexed=false, rank=null`). 현재 구조의 가장 큰 결함이 이것이다.
- `competitors` 는 주간 SEO 분석(§9)의 입력이다. 이긴 글의 URL을 남겨야 나중에 열어볼 수 있다.
- 발행 후 D+1, D+3, D+7, D+14, D+30 에 체크한다. 매일 전부 재검색하면 비용이 선형으로 는다.

### 4.2.1 검색 물량 — 오해 방지

**`keywords` 6,139행은 검색 대상이 아니다.** 그것은 아직 쓰지 않은 인물까지 포함한 후보
명단이다. 검색 대상은 **발행된 원고**뿐이다.

실측(2026-08-15 기준): 최근 30일 발행 440건, **하루 평균 14.7건**.

정상 상태의 하루 검색량 = 하루 발행량 × 체크 횟수 5회 ≈ **75건/일**.

현재 크론(전일 발행분 1회)의 약 5배지만 절대량이 작아 단일 Chromium 직렬 처리로 충분하다.
기존 발행분 1,397건을 매일 재검색하는 일은 없다 — 소급 측정을 한다면 현재 상태 1회
스냅샷으로 끝낸다(§13).

### 4.3 기존 크론과의 관계

기존 검색·스크린샷·Discord 모듈을 **재사용**한다. Discord 발송 동작은 그대로 둔다 —
사람이 매일 보는 화면을 바꾸지 않는다.

변경점은 셋이다.

1. 미노출 키워드도 `skip` 하지 않고 `indexed=false` 로 기록한다.
2. 노출 시 순위와 상위 5건 경쟁 문서를 함께 파싱해 저장한다.
3. **구동원을 RSS 에서 `articles` 테이블로 바꾼다.** 초안은 "저장 단계만 추가"로 잡았으나,
   RSS 는 어제 발행분의 제목만 주고 `article_id` 를 주지 않는다. KPI 를 원고에 붙일 수 없고
   D+3/7/14/30 도 표현할 수 없다. `articles` 는 `id`·`person_name`·`publish_date`·`published_at`
   을 모두 갖고 있어 그대로 쓸 수 있다.
   부수 효과: `lib/naver-search/rss.ts` 가 죽은 코드가 되어 삭제된다(다른 RSS 사용처는 각자
   자기 파서를 갖고 있다).

순위는 네이버 DOM 구조가 아니라 **HTML 등장 순서의 블로그 포스트 링크 목록**에서 센다.
DOM 구조는 자주 바뀌지만 링크 형태는 안정적이고, 목적이 절대 순위가 아니라 추세 비교라
이 정의로 충분하다. 링크가 하나도 안 잡히면 `note='parse-failed'` 로 남겨 조용히 삼키지 않는다.

## 5. B — 지식 그래프

### 5.1 인물 노드는 새로 만들지 않는다

`keywords` 테이블(6,139행)이 이미 인물 명단이자 중복 검사의 원장이다. 그래프가 별도 인물
목록을 만들면 두 원장이 갈라진다 — `person_name` 로마자/한글 문제(project_person_name_romaji_dedup)와
같은 사고가 재발한다.

`mih_kb_entities` 에 인물 노드를 두되 **`keyword_id` 로 `keywords` 를 참조**하고,
중복 판정 권한은 계속 `keywords` 와 `scripts/check-keyword.mjs` 에 둔다. 엣지가 인물과
비인물을 균일하게 다룰 수 있으려면 인물도 엔티티 테이블에 있어야 한다.

### 5.2 노드·관계 종류

| kind | 예 | 비고 |
|---|---|---|
| `person` | 아이유, 팬타곤 키노 | `keyword_id` 필수 |
| `group` | 팬타곤, TWS | |
| `agency` | 큐브엔터테인먼트 | 소속사 이동이 잦다 → 만료 관리 대상 |
| `song` | 대표곡 | |
| `program` | 방송·프로그램 출연 | |
| `award` | 수상 | |
| `event_type` | 대학축제, 기업행사, 지역축제, 페스티벌, 프라이빗 | 고정 목록 |
| `genre` | 발라드, 힙합, 트로트, 아이돌, 강연 | 고정 목록. `keywords.category` 와 정합 |

| rel | 방향 | 예 |
|---|---|---|
| `member_of` | person → group | |
| `signed_to` | person/group → agency | `attrs.since`, 만료 관리 |
| `released` | person/group → song | |
| `appeared_in` | person → program | |
| `won` | person → award | |
| `performed_at` | person → event_type | **기사로 확인된 실제 출연 이력만.** 추정 아님 |
| `similar_to` | person → person | 장르·무대 성격 유사. 후속 추천 서비스의 재료 |
| `has_genre` | person → genre | |

### 5.3 사실(claims) — 검증 단위

사실 1건 = 1행. 엔티티 `attrs` 에 묻지 않는 이유는 사실 1건이 **출처·검증·유효기한의 단위**이기 때문이다.

```sql
CREATE TABLE IF NOT EXISTS mih_kb_claims (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_id   uuid REFERENCES mih_kb_entities(id) ON DELETE CASCADE,
  edge_id     uuid REFERENCES mih_kb_edges(id) ON DELETE CASCADE,
  claim       text NOT NULL,
  kind        text NOT NULL DEFAULT 'fact',   -- fact | needs-check
  source_id   uuid REFERENCES mih_kb_sources(id),
  quote       text,                            -- 출처에서 그대로 따온 문장
  status      text NOT NULL DEFAULT 'draft',   -- draft | verified | rejected | conflict | stale
  confidence  smallint,
  verified_at timestamptz,
  expires_on  date,
  note        text,                            -- rejected/conflict 사유. 재수집 낭비 방지
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS mih_kb_claims_key_idx
  ON mih_kb_claims (entity_id, claim) NULLS NOT DISTINCT;
```

### 5.4 출처 등급 (연예인 도메인)

병원 도메인과 달리 "공식 홈페이지가 진실"이 성립하지 않는다.

| tier | 무엇 |
|---|---|
| 1 | 본인·소속사 공식 채널 (공식 인스타·공식 유튜브·소속사 공지) |
| 2 | 포털 인물정보, 음원 플랫폼(멜론·지니) 아티스트 페이지, 공공·협회 자료 |
| 3 | 보도자료 |
| 4 | 언론 기사 |
| 5 | 커뮤니티·팬 위키·개인 블로그 — **근거로 쓰지 않는다** |

tier 4만 근거인 사실은 `kind: needs-check`. tier 5 단독은 적재하지 않는다.

### 5.5 만료·재확인 — 이 도메인의 핵심 차이

연예인 정보는 계속 바뀐다. 소속사 이동, 그룹 탈퇴·해체, 활동 중단, 개명. 병원 정보보다
훨씬 빠르게 낡는다. 공개 인물 DB(§11)를 열었을 때 옛 정보가 그대로 떠 있는 것이 이 프로젝트의
최대 대외 리스크다.

따라서 **사실 종류별로 재확인 기한 기본값을 강제**한다.

| 사실 종류 | 기본 `expires_on` | 이유 |
|---|---|---|
| 소속사(`signed_to`) | 6개월 | 이동이 가장 잦다 |
| 그룹 멤버십(`member_of`) | 6개월 | 탈퇴·해체 |
| 활동 상태(활동 중/중단/군복무) | 3개월 | |
| 최근 활동·컴백 | 3개월 | 정의상 최신성이 전부 |
| 데뷔연도·본명·대표곡·수상 | 없음 (불변) | |
| 과거 출연 이력(`performed_at`) | 없음 (불변) | 과거 사실은 안 바뀐다 |

기한이 지나면 자동으로 `stale` 로 내려가고, **`verified` 가 아닌 사실은 원고에도 공개
페이지에도 나가지 않는다.**

### 5.6 신호(signals) — 점수화하지 않는다

행사 적합성·예산대를 사람이 6,139명에게 입력하는 설계는 돌아가지 않는다. 그렇다고
자동 산출한 점수를 단정하지도 않는다 — 점수는 보정 부담을 만들고, 근거가 사라지며,
신인이 전부 "부적합"으로 깔린다.

**대신 신호를 구조화해 저장하고, 화면에는 근거를 그대로 나열한다.**

```sql
CREATE TABLE IF NOT EXISTS mih_kb_signals (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_id   uuid NOT NULL REFERENCES mih_kb_entities(id) ON DELETE CASCADE,
  metric      text NOT NULL,      -- instagram_followers | youtube_views_median | recent_activity_12m
                                  -- | event_type_count:대학축제 | debut_year | article_count_12m
  value       numeric,
  unit        text,
  source_id   uuid REFERENCES mih_kb_sources(id),
  observed_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS mih_kb_signals_entity_idx ON mih_kb_signals (entity_id, metric, observed_at DESC);
```

수집 가능한 신호만 담는다: 팔로워 수, 유튜브 최근 업로드·조회수 중앙값, 최근 12개월 활동
건수, 기사로 확인된 행사 유형별 출연 횟수, 데뷔 연차, 기사 노출량.

**신호가 없는 것과 값이 0인 것은 다르다.** 미수집은 행을 만들지 않는다(0으로 채우지 않는다).

후속 추천 서비스는 "점수 높은 순"이 아니라 **조건 필터 + 근거 제시**로 동작한다 —
"장르가 힙합이고, 최근 12개월 내 대학축제 출연이 기사로 2회 이상 확인된 인물" 같은 형태.
정렬이 필요하면 단순 규칙(신호값 정렬)을 쓰되, 그 값을 화면에 종합 점수로 표시하지 않는다.

### 5.7 출연료

**어떤 형태로도 금액을 추정·저장·표시하지 않는다.** 내부 등급조차 이번 범위에서 뺀다.
필요해지면 후속 단계에서 별도 판단한다. 근거 없는 금액이 어딘가에 남으면 아티스트·소속사와의
분쟁 소재가 되고, 이미 작성 지침도 "추정 금액을 단정하지 않는다"를 명시하고 있다.

## 6. C — 에이전트 체인

### 6.1 구성

오케스트레이터는 기존 `naver-article` 스킬을 개조한다. **오케스트레이터 컨텍스트에서
원고 본문을 직접 쓰지 않는다** — 4,000자 원고와 KB 근거가 컨텍스트를 다 먹는다.

| 단계 | 에이전트 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 1 수집 | `mih-researcher` | 웹 검색·공식 SNS 크롤 → 사실을 `draft` 로 적재, 신호 적재, 인스타 이미지 수집 | 판정하지 않는다 |
| 2 검증 | `mih-verifier` | 출처를 다시 열어 `quote` 대조 → `verified`/`rejected`/`conflict` | 새 사실을 만들지 않는다 |
| 3 작성 | `mih-writer` | `verified` 사실만 근거로 SE3 HTML 작성 (`write-article` 스킬 그대로 사용) | 근거 없는 문장을 쓰지 않는다 |
| 4 검수 | `mih-reviewer` | `03_원고_검토_지침` + `check:article` + 근거 없는 문장 색출 + 임베딩 지표 | 스스로 고치지 않는다 (지시만) |

체인 진입 전 `check-keyword.mjs` 중복 게이트는 **그대로 유지**한다. 이 게이트는 체인 밖의
선행 조건이다.

### 6.2 부모에게 돌려주는 것

각 서브에이전트는 **요약만** 반환한다. 크롤 원문·전체 사실 목록·원고 본문을 올리면
오케스트레이터 컨텍스트가 터진다.

```
수집: 출처 5건(tier1:2, tier2:2, tier4:1) / 엔티티 9건 신규 / 사실 23건 draft / 신호 6건
      needs-check 2건: <요약>
      확인 못 함: 2026년 소속사 (공식 채널에 언급 없음)
검증: verified 17 / rejected 4 / conflict 2 / 보류 0
      conflict: "소속사 A" — 포털 인물정보 vs 2026-03 기사
작성: slug, 4,120자, 이미지 4, iframe 2, KB 사실 15건 사용
검수: pass | needs-fix + 지시 목록
```

### 6.3 재작성 루프

`needs-fix` 면 지시를 그대로 `mih-writer` 에 되돌린다. **최대 2회.** 두 번 고쳐도 남으면
사용자에게 남은 항목을 보고하고 멈춘다.

### 6.4 실행 기록

nj-ad 의 `hbs_runs`/`hbs_run_steps` 패턴을 그대로 가져온다. **기록은 오케스트레이터만 남긴다** —
서브에이전트가 자기 실행을 기록하면 실패로 죽었을 때 종료 기록이 안 남는다.

```sql
CREATE TABLE IF NOT EXISTS mih_runs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  keyword_id uuid REFERENCES keywords(id),
  agency text,
  started_at timestamptz NOT NULL DEFAULT now(),
  ended_at timestamptz
);

CREATE TABLE IF NOT EXISTS mih_run_steps (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id uuid NOT NULL REFERENCES mih_runs(id) ON DELETE CASCADE,
  step text NOT NULL,          -- 수집 | 검증 | 작성 | 검수
  agent text,
  attempt smallint NOT NULL DEFAULT 1,
  status text NOT NULL DEFAULT 'running',  -- running | done | failed
  metrics jsonb NOT NULL DEFAULT '{}',
  note text,
  started_at timestamptz NOT NULL DEFAULT now(),
  ended_at timestamptz
);
```

**metrics 고정 키** — 집계가 이름에 의존한다. 지어내지 않는다. 값이 없으면 키를 뺀다.

| 단계 | 키 |
|---|---|
| 수집 | `entities` `claims` `sources` `signals` `dupSkipped` |
| 검증 | `verified` `rejected` `conflict` `stale` |
| 작성 | `chars` `images` `iframes` `kbClaimsUsed` |
| 검수 | `result`(`pass`\|`needs-fix`) `issues`(문자열 배열) `simQuery` `simMaxSelf` |

`issues` 에는 `check:article` 이 쓰는 코드를 **그대로** 넣는다. 새 코드 체계를 만들지 않는다.
`check:article` 이 못 잡는 것만 접두어를 붙인다 — 근거 없는 문장은 `kb:미근거`,
임베딩 지표 이탈은 `emb:쿼리유사도낮음` / `emb:자기유사도높음`.

**체인을 중간에 멈출 때도 그 run 을 닫는다.** 열어 둔 채 끝내면 죽은 세션과 구분되지 않고
품질 집계에서 통째로 빠진다 — 정작 가장 봐야 할 실패 사례가 사라진다.

### 6.5 대량 생산 시의 이탈구

"계정별 N개씩" 대량 요청에서는 비용이 선형으로 는다. 체인 전체를 도는 것이 기본이되,
사용자가 명시적으로 요청하면 수집·검증을 건너뛰고 기존 `verified` 사실만으로 작성할 수 있다
(그 인물의 `verified` 사실이 10건 이상일 때만). 건너뛴 사실은 보고에 명시한다 —
조용한 축소는 "다 했다"로 읽힌다.

## 7. D — 임베딩 기반 검증

### 7.1 왜 필요한가

현재 `check:article` 의 핵심 지표는 `섭외` 밀도 3~5회/1000자다. 이것은 **대리 지표**다.
실제로 재야 하는 것은 "이 문서가 `<인물명> 섭외` 라는 쿼리의 의미에 얼마나 가까운가"이며,
AI 검색·AI 브리핑이 인용 대상을 고르는 방식도 이쪽이다.

nj-ad 가 이미 로컬 임베딩을 돌리고 있다(`lib/hbs/embed.ts`, 로컬 ONNX, 무과금, pgvector `<=>`).
**가져오는 것은 실행 구조(로컬 ONNX 적재·배치 임베딩·pgvector 저장)이지 모델이 아니다.**

### 7.2 모델 선정 — 한국어 전용 요구사항

nj-ad 의 jina-clip-v2 는 **멀티모달(이미지+텍스트) 모델**이고, 거기서는 마커 문장으로 사진을
찾는 용도다. 해당 파일 주석에 "한국어 쿼리가 영어보다 확연히 약하다"는 실측이 남아 있고,
그래서 그 프로젝트는 검색 쪽에 영어 문장(`desc_en`)을 쓴다.

**우리 원고는 전부 한국어이고 이미지 매칭이 필요 없다.** 우회로가 없으므로 이 모델을 쓰지 않는다.

필수 조건 세 가지:

| 조건 | 왜 |
|---|---|
| **한국어 성능** | 원고·쿼리·경쟁 문서가 전부 한국어다. 영어로 번역해 재는 우회는 의미를 왜곡한다 |
| **긴 컨텍스트 (8k 토큰급)** | 본문이 3,800~6,000자. 512 토큰 모델은 도입부만 읽고 자른다 — `simQuery` 가 "글 전체"가 아니라 "앞부분" 유사도가 된다 |

**라이선스 제약은 두지 않는다.** 이 지표는 원고 품질 판단을 위한 내부 분석용이고 모델 출력을
재배포하지 않는다. CC BY-NC 계열(`jina-embeddings-v3` 등)도 후보에 포함한다.

후보(구현 시 실측 비교):

- `BAAI/bge-m3` — 8192 토큰, 다국어, MIT
- `nlpai-lab/KURE-v1` — bge-m3 기반 한국어 파인튜닝
- `dragonkue/BGE-m3-ko` — 한국어 파인튜닝
- `jinaai/jina-embeddings-v3` — 8192 토큰, 다국어 **텍스트** 전용(멀티모달 clip-v2 와 다른 모델),
  retrieval.query / retrieval.passage task LoRA 내장. CC BY-NC

512 토큰 제약이 있는 `multilingual-e5-*` 계열은 조각(§7.6) 전용으로는 쓸 수 있으나
문서 전체 지표에는 부적합하다. 모델을 둘로 나누면 두 지표의 자가 달라지므로 하나로 통일한다.

### 7.3 모델 선정 실측 — 선행 작업 (acceptance test)

**모델 선정은 감으로 하지 않는다.** 다만 **시험은 실제 용도와 같아야 한다.**

먼저 폐기한 시험을 기록해 둔다. 초안은 `"<인물명> 섭외"` 로 1,402건에서 그 인물 원고를
찾는 Recall@1 을 쓰려 했으나, **그것은 고유명사 검색 시험이지 의미 유사도 시험이 아니다.**
희귀 인물명은 토크나이저가 쪼개 버려 어떤 모델이든 약하고, 우리는 애초에 임베딩으로
"인물 원고를 찾는" 일을 하지 않는다. 네 지표(§7.5)는 전부 **같은 자로 잰 상대 비교**다.
잘못된 시험으로 쓸 만한 모델을 떨어뜨리는 것이 더 큰 손해다.

**실제 용도에 맞는 시험 세 가지** — 전부 지금 있는 데이터로 즉시 돌아간다.

| 시험 | 방법 | 정답지 | 무엇을 보증하나 |
|---|---|---|---|
| ① 장르 판별 | 원고 전문 임베딩 후, 같은 `keywords.category` 원고 쌍과 다른 category 쌍의 유사도 분포를 비교 | `keywords.category` (이미 라벨링돼 있음) | 고유명사와 무관한 **순수 의미 판별력**. 두 분포가 겹치면 이 모델로는 아무것도 못 잰다 |
| ② 조각 판별 | 한 원고 안에서 FAQ 답변 조각과 해시태그·CTA 조각의 쿼리 유사도를 비교 | 자명 (FAQ 가 더 가까워야 함) | `simChunk`(§7.6)가 조각 품질을 구분할 수 있는가 |
| ③ 자기 유사도 분포 | 1,402건 전체 쌍의 유사도 분포를 그린다 | 없음 (분포 자체를 본다) | `simMaxSelf` 임계를 잡을 수 있는가. 전 쌍이 0.9 위에 뭉쳐 있으면 판별 불가 |

판정: **①에서 두 분포가 통계적으로 갈리지 않는 모델은 탈락.** ②·③은 임계값 설정을 위한
분포 파악이 목적이며 단독 탈락 사유가 아니다.

부수 효과: 이 배치가 그대로 `simMaxSelf`(§7.5 4번)의 기준 벡터 저장소가 된다.

비용: 로컬 후보는 과금 없음, 후보당 1~2시간 배치.

### 7.4 실패 시 사다리 — 측정을 포기하지 않는다

후보 모델이 §7.3 ①을 통과하지 못해도 **임베딩 지표를 빼지 않는다.** 상위 노출이 1순위이고,
측정 없이는 개선 여부를 알 수 없기 때문이다. 아래 순서로 내려간다. 위 칸이 아래 칸보다 싸다.

| # | 조치 | 근거 |
|---|---|---|
| 1 | **프리픽스·정규화 점검** | BGE/E5 계열은 `query:` / `passage:` 비대칭 프리픽스가 필수다. 안 붙이면 성능이 크게 떨어진다 — 실패의 가장 흔한 원인이며 코드 한 줄이다 |
| 2 | **쿼리 확장** | `"OOO 섭외"` 는 2어절이라 임베딩이 불안정하다. 검색 의도를 문장으로 펼쳐 넣는다 — `"OOO을 행사에 섭외하는 방법과 비용, 적합한 행사 유형"` |
| 3 | **다른 로컬 모델** | §7.2 후보를 순회. 라이선스 제약이 없어 선택지가 넓다 |
| 4 | **유료 API 임베딩** | OpenAI `text-embedding-3-large`, Voyage, Cohere multilingual. **전체 코퍼스 1회 재적재가 1~2천 원 수준**(1,402건 × 약 3k 토큰 ≈ 4M 토큰). 비용은 사실상 제약이 아니다 |
| 5 | **하이브리드 / 재순위** | 임베딩 + BM25 키워드 결합, 또는 `bge-reranker-v2-m3` 같은 cross-encoder 재순위. 소량이라 감당 가능 |
| 6 | **자를 바꾼다** | 여기까지 실패하면 유사도를 버리고 **정보 축 커버리지**로 대체한다 — 경쟁 상위 글이 다루는 주제 축을 지식 그래프 엔티티 종류로 뽑고, 우리 원고가 덮은 축의 개수를 센다. 벡터 없이도 "경쟁 글보다 정보가 많은가"를 잴 수 있다 |

**6번까지 내려가도 측정 항목 자체는 유지된다.** 바뀌는 것은 재는 방법이지 재는 대상이 아니다.

### 7.5 네 가지 지표

| # | 지표 | 무엇을 재나 | 쓰임 |
|---|---|---|---|
| 1 | `simQuery` | 원고 전문 ↔ `"<인물명> 섭외"` | 주제 정합성 |
| 2 | `simChunk[]` | **섹션·FAQ 답변 각각** ↔ 쿼리 | AEO 핵심 (§7.6) |
| 3 | `simCompetitor` | 상위 노출 경쟁 문서 ↔ 쿼리, 우리 값과 비교 | 주간 분석 입력 |
| 4 | `simMaxSelf` | 신규 원고 ↔ 기존 원고 1,402건 중 최댓값 | 양산형 신호 탐지 |

### 7.6 조각 단위가 핵심

AI 검색은 문서 전체가 아니라 **답변에 쓸 조각(passage)** 을 뽑는다. FAQ 답변 하나하나가
그 인용 단위다. 따라서 조각을 따로 임베딩해 각 조각이 **홀로 떨어져 나갔을 때도 쿼리에
답이 되는지**를 잰다. 값이 낮은 조각은 AI 가 가져가지 않는다.

이것이 기존 지침의 "FAQ 답변 첫 문장은 결론으로 시작한다"를 기계로 검증하는 방법이다.

### 7.7 자기 유사도 — "다 비슷하다" 문제의 측정

`simMaxSelf` 가 임계 이상이면 검수에서 `emb:자기유사도높음` 으로 걸린다. 기존 원고와
너무 비슷한 원고는 반복 신호가 되어 역효과라는 것이 작성 지침의 전제인데, 지금은 그것을
사람 눈으로도 기계로도 확인하지 않고 있다.

### 7.8 정직하게 짚을 것 — 이 숫자는 절대 기준이 아니다

우리가 계산하는 코사인 유사도는 **네이버가 쓰는 모델로 잰 값이 아니다.** 네이버 내부
임베딩 모델과 랭킹 함수는 공개되지 않았다. 따라서:

- ❌ "0.8 넘으면 상위노출된다" — 성립하지 않는다.
- ✅ "이 쿼리에서 이긴 경쟁 글은 0.71, 우리 글은 0.52다" — 같은 자로 잰 상대 비교라 유효하다.

### 7.9 지표별 조치 — 보완이냐 경고냐

지표가 낮다고 **발행을 막지 않는다.** 대신 **구체적인 보완 지시를 만들 수 있는 지표만
재작성 루프를 돌린다.** 기준은 하나다 — *어디를 어떻게 고치라고 말할 수 있는가.*

| 지표 | 낮을 때 조치 | 지시 가능한가 |
|---|---|---|
| `simChunk[]` 개별 조각 | **보완 후 발행.** 해당 조각만 다시 쓴다 | ✅ "이 FAQ 답변은 홀로 떨어지면 질문에 답이 안 된다 — 결론 문장을 앞에 세우고 변수 N개를 채워라" |
| `simMaxSelf` 높음 | **보완 후 발행.** 겹치는 원고·섹션을 지목해 다른 정보로 교체 | ✅ "이 원고의 섹션 4가 `<기존 slug>`의 섹션 4와 겹친다 — KB 사실 X·Y로 교체하라" |
| `simQuery` 전체 낮음 | **경고만.** 재작성 루프를 돌리지 않는다 | ❌ "글 전체가 주제에서 멀다"로는 어디를 고칠지 알 수 없다 |
| `simCompetitor` 열세 | **경고만.** 주간 분석(§8)의 입력으로만 쓴다 | ❌ 개별 원고 차원의 조치가 아니다 |

**`simQuery` 로 재작성을 돌리면 안 되는 이유**는 비용이 아니라 방향이다. 문서 전체 유사도를
올리려는 압력은 `섭외` 를 더 집어넣는 편법으로 귀결되고, 그것은 반복 신호가 되어 역효과다
(작성 지침이 밀도 상한을 두는 이유와 같다). 지표 최적화가 실제 품질과 어긋나는 전형적인 지점이다.

보완은 **최대 1회**, 기존 재작성 한도 2회 안에서 소비한다. 보완 후에도 남으면 그대로 발행하고
`mih_run_steps.metrics.issues` 에 남긴다 — 주간 분석이 그 목록을 본다.

### 7.10 임계값은 잠정값이다

**임계값을 처음부터 하드 검사(발행 차단)로 걸지 않는다.** `check:article` 의 하드 실패 목록에
넣지 않는다는 뜻이다. §7.9의 보완 루프는 체인 내부에서 돌고, 보완에 실패해도 발행은 막지 않는다.

초기 임계값은 **첫 50건의 분포에서 하위 20% 지점**으로 잡고, §8의 상관 검증 결과에 따라 조정한다.
값을 먼저 정해놓고 원고를 맞추는 순서가 되면 안 된다.

## 8. E-1 — 주간 SEO 분석 에이전트

체인 밖에서 도는 다섯 번째 에이전트(`mih-seo-analyst`). **매 원고마다 부르지 않는다.**
목표 쿼리가 `"<인물명> 섭외"` 로 고정이라 원고별 쿼리 조사가 불필요하고, 매 편 붙이면
비용만 는다.

주 1회, 다음을 한다.

1. `mih_serp_checks` 에서 지난 주 **미노출·저순위 원고**를 모은다.
2. `indexed=false` 묶음과 `rank` 하위 묶음을 **분리해서** 본다 — 원인이 다르다.
3. 저순위 묶음에 대해 `competitors` 의 이긴 글을 열어 우리 글과 비교한다
   (구조·정보 축·분량·조각 구성).
4. **지표 상관 검증** — `simQuery`·`simChunk`·`simMaxSelf`·글자수·KB 사실 수가 실제 순위와
   상관이 있는지 확인한다. **상관이 없는 지표는 버린다.** 이 검증이 없으면 그럴듯한 숫자를
   보면서 아무것도 안 고치게 된다.
5. 산출물: 주간 리포트 + `docs/지침/` 수정 제안. **지침 수정은 사람 승인 후 반영한다.**

데이터가 없으면 아무 말도 못 한다. **KPI 2~3주 축적 후 가동한다.**

## 9. E-2 — 알고리즘 변경 추적

월 1회 정기 작업. 네이버 공식 채널(네이버 서치앤테크 블로그, 네이버 다이어리, 검색 공식 공지)을
확인해 변경 발표를 요약하고, 작성 지침에 미치는 영향을 정리한다.

**지침 파일을 자동으로 고치지 않는다.** 제안까지만 하고 사람이 승인한다. 자동 반영하면
어느 날 갑자기 원고 형태가 바뀌어 있게 되고, 그 시점 전후의 KPI 비교가 무의미해진다.

## 10. 데이터 흐름 요약

```
1. 인물 선정 (pick-keywords + check-keyword 중복 게이트)   ← 기존 그대로
2. mih-researcher  → mih_kb_sources / entities / edges / claims(draft) / signals
3. mih-verifier    → claims: draft → verified | rejected | conflict
4. mih-writer      → verified claims 만 근거로 SE3 HTML (write-article 스킬)
5. mih-reviewer    → check:article + kb 근거 대조 + 임베딩 지표 → pass | needs-fix(최대 2회)
6. publish         → articles
7. serp 크론       → mih_serp_checks (D+1/3/7/14/30, 미노출도 기록)
8. mih-seo-analyst → 주간 리포트 + 지침 수정 제안 (사람 승인)
```

## 11. 후속 단계 (이번 설계 범위 밖)

각각 별도 설계를 거친다. 그래프가 실제로 어떻게 차는지 본 뒤에 설계한다.

| 단계 | 무엇 | 선행 조건 | 주된 리스크 |
|---|---|---|---|
| 2 | 섭외 추천·매칭 (**내부용 먼저**) | **노출 KPI 개선 추세 확인** + 그래프에 인물 200명 이상 | 없음 (내부라 오답 허용) |
| 3 | 공개 인물 데이터베이스 | 2단계로 정확도 검증 완료 | **대외 리스크 최대** — 오정보 공개, 초상권·이미지 라이선스 |
| 4 | 문의 자동응답 | 2·3단계 안정화 | 틀린 답이 고객에게 직행 |

**모든 후속 단계의 공통 선행 조건은 노출 KPI 개선이다.** 노출이 안 되는 상태에서 서비스를
얹으면 재료가 되는 데이터를 신뢰할 근거가 없고, 인력·비용이 1순위에서 빠져나간다.

3단계를 2단계보다 뒤에 두는 이유는 순서상 편해서가 아니라, **내부 사용 기간이 곧 정확도
검증 기간**이기 때문이다. 검증 없이 1,400명 분량을 외부에 여는 것은 되돌리기 어렵다.

## 12. 지키는 선

- 원고는 `verified` 사실만 근거로 쓴다. `draft` 를 쓰면 검증 절차가 무의미해진다.
- 출연료 금액은 추정·저장·표시하지 않는다.
- 실제 섭외 후기(날짜·장소·현장 반응)를 지어내지 않는다 — 기존 지침 유지.
- 하이브 계열 아티스트는 그래프에도 신규 적재하지 않는다.
- 임베딩 지표로 **발행을 막지 않는다.** 구체적 보완 지시가 가능한 지표(조각별 유사도,
  자기 유사도)만 보완 루프를 돌리고, 문서 전체 유사도는 경고로 남긴다(§7.9).
- 임베딩 모델은 §7.3 장르 판별 시험을 통과한 것만 쓴다. **통과 못 하면 §7.4 사다리를 내려간다 —
  측정을 포기하지 않는다.**
- 상위 노출이 1순위다. 부가 서비스는 노출 KPI 개선이 확인된 뒤에 착수한다.
- 기존 발행 원고(`published_at` 있음)는 손대지 않는다 — 네이버에 박제됐다.
- 지침 파일 수정은 항상 사람 승인을 거친다.
- 체인이 멈출 때도 실행 기록을 닫는다.
- `발행` 여부는 사람이 정한다. 에이전트가 자동 발행하지 않는다.

## 13. 열린 질문

- 임베딩 모델 최종 선정 — §7.3 실측으로 확정한다. **구현 착수 전 첫 작업이다.**
  모든 후보가 떨어지면 §7.4 사다리를 순서대로 내려간다.
- `mih_serp_checks` 의 순위 파싱 — 네이버 통합검색 DOM 구조 변경에 취약하다. 파싱 실패 시
  `indexed` 만 남기고 `rank=null, note='parse-failed'` 로 기록해 실패를 조용히 삼키지 않는다.
- 기존 1,402건에 대한 KPI 소급 측정 여부 — 발행일이 오래된 건은 D+N 체계가 안 맞는다.
  현재 노출 상태만 1회 스냅샷으로 잡는 방안을 별도 검토.
